Recommended design work

Keep the warmth. Make the controls easier to find.

These are proposals, not implemented app changes. Priority follows everyday usefulness and the screenshots, rather than adding decorative space or more service cards.

First

Give Settings a short category index

Use Appearance, Momo, Weather & time, Photos, Calendars and Device as six clear destinations. Keep the category index visible while a panel is open and add a clear back route. The existing page requires a long scroll past the wardrobe to reach everyday connection controls.

Success looks like: Every category is reachable in one tap from Settings; direct links from setup and service tabs still land on the correct section.

First

Put each control beside the feature it changes

Photos should own source, style, speed and idle timing, with one Settings link to the same controls. Calendar management should open within Calendar. Avoid two different settings surfaces for one feature or sending the owner into an unrelated long page.

Success looks like: Starting from a feature screen, changing its most common preference takes at most two deliberate taps; there is one authoritative editor per preference.

First

Make status useful and readable

Use one status pattern per service: Not set up → Checking → Updated → Saved/offline → Needs attention. The rail's Connected only reflects browser network availability; it does not prove Gmail, Calendar or Home works. Replace technical full timestamps with concise local times and show details on demand.

Success looks like: A failure says what remains usable and offers a specific recovery action. Successful credential storage is never described as verified functionality.

First

Keep warm colour, increase functional legibility

Preserve soft surfaces, serif headings and Momo. Enlarge the smallest state/help text and improve its token contrast where needed instead of turning every panel high contrast. Make primary and secondary actions consistent; keep focus, selected date and destructive confirmation distinct.

Success looks like: Use 44×44 CSS pixels as the minimum design target for frequent touch controls, with 48–56px preferred on the frame. Measure text contrast on actual surfaces and retain all six light/dark pairs.

Next

Design for the frame before the desktop

Treat 1280×720 CSS pixels as the primary canvas. Overview and the core Calendar view should fit without page scrolling; long Settings forms can scroll deliberately. For Weather, trade some hero height for breathing room below the five-day row. On narrow screens, use a compact navigation treatment and lead with the useful content.

Success looks like: Check the frame, desktop and narrow widths with long titles, six calendars, a full photo cache, visible errors and enlarged text. No horizontal overflow or clipped actionable status.

Later

Keep the rail calm, but make optional apps optional

Keep the four everyday destinations—Overview, Weather, Photos, Calendar—easy to scan. Let households hide Home or YouTube from the rail if unused, keeping Settings available. Keep Momo in the rail and wardrobe controls in Settings; extra mascot shortcuts would add clutter.

Success looks like: The default rail stays familiar; hiding optional destinations never strands an active screen or removes its recovery path.

Accessibility reference: use 44×44 CSS pixels as a generous touch-design target, drawn from WCAG's enhanced target-size criterion (AAA), not a claim of current AA compliance. Normal text has a 4.5:1 contrast benchmark; large text 3:1. Skylit's current contrast tests cover the optional High contrast palette only. W3C target size · W3C contrast.

OverviewLayout recommendations

Suggested structure: Clock + weather | photo stack + three events; the same grid adapts when a source is absent.

Observed: The current four-part composition is the strongest screen. Photo prints deliberately overlap the agenda, while the weather artwork and oversized clock supply the visual identity.

  1. Keep the clock/weather left and photos/three-event agenda right. Add a modest safe gap below the prints so longer Upcoming headings or warnings never compete with the photograph edges.
  2. Make a complete weather card and each upcoming-event row a generous drill-down target; retain a visible, labelled route such as Forecast or Calendar instead of relying only on small arrows.
  3. For absent photos or calendars, rebalance the space and provide one contextual setup action. Keep healthy timestamps out of Overview; show saved/offline warnings without expanding the card unpredictably.
WeatherLayout recommendations

Suggested structure: Heading/status → current conditions + compact metrics → hourly row → five-day row.

Observed: Current conditions are clear, but the hero and three metric cards use most of the frame height. At 720 CSS pixels the footer sits below the visible canvas; hour/day supporting labels are small.

  1. Reduce the hero's vertical padding/height slightly and reserve a clear area for both forecast rows. Keep the condition illustration; use compact rain/wind/sunset tiles beside it or underneath it.
  2. Increase hourly time and precipitation labels; align five-day highs/lows in consistent columns. When no city is set, replace the seven-column forecast placeholder with one full-width Choose city state so its copy does not wrap into a narrow stack.
  3. Pair the city with a Change city action and keep one refresh/status line near the heading. In offline/error states, display Saved forecast plus its age and a Retry action above the data.

  1. Use the full content width for thumbnails while settings are closed. Put a labelled Photo settings button in the header and open a broad side panel or dedicated subpage only when needed.

Observed: The full-screen photo treatment and fading theme controls are effective. Browse and playback share the same control bar, while collage crops pictures to fill its slots.

Observed: The expanded panel combines styling, credentials, cache limits and disconnect in one narrow column. A first-time owner has to interpret several unrelated controls at once.

Prioritized brainstorm

Deepen photos and plans, then add one household utility.

P0 = foundation/verification before expanding. P1 = recommended next product work. P2 = useful follow-ons after the daily flows are solid. Effort is a relative estimate: S = focused UI/preference change; M = behaviour across UI/storage/native layers; L = new integration or policy. These are not delivery-time estimates.

First pass: navigation and trust

Settings categories; feature-local controls; concise state/retry labels; frame readability. Run the missing reliability/device acceptance checks alongside this work.

Second pass: better photos and plans

Adjustable mail refresh, photo favourites/hide/fit, Today/Week agenda and source visibility. These deepen the two most useful existing features.

Third pass: one new household utility

Ship the local note/shopping checklist, then quiet hours/privacy pause. Learn from daily use before adding phone sync, voice or more service integrations.

P0

Service status and guided recovery

Effort M

Foundation / extends every integration

Why: A network indicator and saved credential do not prove a feature works. Failures need a useful next action, not a generic Connected label.

Smallest useful version: A local status panel with last successful weather fetch, calendar parse, mail check and cached-picture count; each service offers Retry or its setup route. Keep Home as owner-verified, never infer remote authentication.

Acceptance: Offline data remains usable; status contains no URLs, mail identity, event details or tokens; each recovery action is tested.

Dependencies: Existing coarse native status and caches; actual-frame verification.

P0

Unattended reliability and acceptance pass

Effort M

Quality work / before expanding scope

Why: Docs explicitly leave long-term mail polling, age pruning, fresh Android setup, live inviter rules and Home operations open.

Smallest useful version: Run a documented multi-day frame soak, upgrade/restart/offline tests, bounded-cache pruning and owner-led real calendar-change/inviter checks. Record results privately with labels only.

Acceptance: No stuck player/import, lost settings, stale-feed resurrection or unbounded cache; unresolved compatibility issues are visible in the UI.

Dependencies: Identified device and owner participation for household tests. No factory reset or destructive reinstall.

P1

Configurable email-photo refresh and progress

Effort M

Extension / Photos

Why: The current importer checks at most once a day after a successful check, plus manual Check now. Newly emailed pictures can feel late.

Smallest useful version: Offer bounded 15-minute, hourly or daily polling; show Checking, last success, received count and actionable failure. Use one in-flight check and network/error backoff; keep the current manual check.

Acceptance: A newly sent test image appears within the selected online window; retries do not overlap or remove the last good cache.

Dependencies: Native PhotoMail scheduling; battery/network/large-inbox testing on the frame.

P1

Effort M

Extension / Photos + Overview

Smallest useful version: Favourite and hide from playback, reversible local choices, Fit/Fill per photo and a shuffle toggle. Let Overview prefer favourites; avoid changing or deleting email messages.

Acceptance: Hidden pictures stay out of all playback modes and Overview; undo works; portrait faces survive Fit; curation survives a harmless refresh.

Extension / Calendar + Overview
